# CLAUDE.md — tab

Project guidance for Claude Code. Read this before changing anything.

## What tab is

A Splitwise replacement for tracking expenses on group trips. No monetisation or ads. The iOS app is live on the App Store (domain tab-it.app) and Supabase production holds real user data. One Expo / React Native app serves iOS and Android; production compatibility and data preservation are mandatory.

Pain points being solved: Splitwise's paywall, ads, and aggressive upsells.

## Architecture at a glance

```
tab/
├── mobile/                 ← The app: Expo SDK 58, React Native, TypeScript, iOS + Android.
│   └── src/
│       ├── app/            ← Expo Router screens (one file per route).
│       ├── domain/         ← Pure money, splitting, balances, presenters. Fully unit-tested; see API.md.
│       ├── data/           ← Local store, sync engine, auth, push, receipts, server-only actions.
│       ├── features/       ← UI shared by several screens.
│       ├── ui/             ← Sage theme, primitives, avatar, menus.
│       └── lib/            ← Config, Supabase client and generated types, ids, date labels.
├── supabase/               ← Postgres schema, RLS, edge functions, local stack scripts, pgTAP tests.
├── contracts/domain/       ← Platform-neutral domain fixtures the domain tests run against.
├── site/                   ← tab-it.app: landing page, invite join page, privacy policy, app-link files.
├── design/                 ← Mockups and logo. Sage palette source of truth.
└── docs/                   ← Specs, ADRs, App Store metadata, legal, working logs, reports.
```

`mobile/README.md` explains the data flow. In short: actions commit to an in-memory store mirrored to per-user SQLite, the sync engine pushes dirty rows and pulls the server's view, and `data/merge.ts` reconciles with the server's conflict rules. Supabase hosts auth, realtime, storage and edge functions; the client is offline-first.

## Tech stack

- **Expo SDK 58**, React Native 0.88 (New Architecture, Hermes), TypeScript strict, Expo Router with native tabs.
- **expo-sqlite** for the local store; **supabase-js** against generated database types (`npm run gen:types`).
- **vitest** for pure TypeScript (domain, merge rules, legacy handoff). The domain runs in Node and on Hermes; it must not use `Intl`, `TextEncoder`, or other APIs Hermes lacks.
- **Supabase** (Postgres 17.6) for auth (Apple Sign-In, Google, email code with Turnstile), realtime, storage, edge functions.
- **Exact money**: decimal strings in rows, `bigint` minor units in maths. Never JavaScript `number` for money. PostgREST money columns are read with `::text` casts.
- **Multi-currency, no FX conversion**: per-currency pairwise balances only.
- **Last-write-wins** with delete-wins and a `write_id` tiebreaker on identical timestamps, matching `set_sync_fields` on the server.
- **Soft delete** on mutable user-visible records (`deleted_at`).
- **Email pre-add** trip joining with an automatic claim on every full sync; invite links at `https://tab-it.app/join/<token>`.
- **Realtime** on the currently viewed trip only, plus pulls on launch, foreground, reconnect and every five minutes.

## Conventions

- **Pure logic lives in `mobile/src/domain/`**: no React, Expo or I/O imports. Plain functions and types; tests sit next to modules as `*.test.ts`.
- **Rows keep Supabase column names.** Local-only bookkeeping uses underscore fields (`_pushed`, `_error`, `_receipt`, `_deleted`, `_readAt`, `_dismissedAt`); see `data/schema.ts`.
- **Every write is local first.** Screens call `data/actions.ts`; only server-only operations (claims, invites, non-group containers, account deletion, person email changes and removal) go through `data/online.ts`.
- **Balance pair-key**: sort UUIDs (lo, hi); a positive amount means hi owes lo. Surface both mirrored rows.
- **Simplified debts** are derived per trip and currency from net positions. They never rewrite expense, split, payment or settlement history.
- **Equal-split remainders** go one minor unit at a time to the lexicographically lowest UUIDs.
- **Exact splits** validate sum, missing participants and extras.
- Use `npx expo install` for Expo-managed packages. `ios/` and `android/` are generated by prebuild and git-ignored; configure native behaviour in `app.config.ts` and config plugins. Native module fixes go in `patches/` via patch-package.
- Format with Prettier (`mobile/.prettierrc.json`).
- **Working log**: substantial implementation or investigation gets a dated, append-only log in `docs/working_log/` (`YYYY-MM-DD-slug.md`). Small edits don't need one.

## Database

- **Production contains real users and must be preserved.** Treat production Supabase, Auth, Storage, Realtime, Edge Functions, and user data as read-only by default.
- Never reset, recreate, drop, truncate, reseed, or bulk-delete production data or schema objects. The repository intentionally provides no database-recreation command.
- Do not run Supabase CLI, MCP, SQL, migrations, Storage cleanup, Auth changes, or remote tests against production unless the user explicitly authorizes that exact operation in the current task and the exact project target has been verified first.
- Development and automated tests must use mocks, a local Supabase stack, or an explicitly isolated non-production project/branch. Development builds read `mobile/.env.development.local` (written by `supabase/scripts/configure_mobile_local.sh`) and never fall back to production configuration.
- The deployed baseline migration is immutable. Do not rewrite or squash an applied migration. Any future database change requires a forward-only, compatibility-preserving migration designed for existing users, tested locally and in an isolated environment, with backup, rollback, and production approval documented before deployment.
- Editable database SQL lives in numbered files under `supabase/sql/`, with `supabase/schema.sql` as a source map. Do not edit SQL, migrations, RLS, functions, Auth, Realtime, or Storage configuration until a production-safe migration plan for the specific change is approved.
- `bash supabase/tests/00_sql_assembly.sh` is a local static source-consistency check and does not connect to a database. pgTAP tests in `supabase/tests/` may run only against an isolated non-production target.
- **RLS is mandatory** on every public table. Every test must verify both the allow and deny path.
- Mutable synced row-tables use `updated_at` + `write_id` (UUID), plus `deleted_at` where the row is soft-deleted.
- Direct `trip_people` insert is forbidden for clients. Trip creation goes through `create_trip_with_self`; adding people goes through `add_trip_person_by_email`; claims go through `claim_trip_people_for_current_email`, which the sync engine calls before each full pull.
- Expense + split writes must be transactional (`create_expense_with_payments_and_splits`); the DB enforces split totals and trip-person references for payers, participants, settlements, categories, and mute prefs.
- Trip access derives from joined `trip_people` rows — RLS policies all read from it.
- Older installed Swift clients keep writing to the same database. Client changes must stay compatible with them.

## Design mockups

Mockups live in `design/` organised by feature area, one subfolder per area:

| Subfolder        | Contents                              |
|------------------|---------------------------------------|
| `mockups/`       | Main app screens and flows            |
| `expense-entry/` | Expense entry UI and flow iterations  |
| `logo/`          | Logo and app icon assets              |

**Naming:** each iteration is `v{N}.html` (`v1.html`, `v2.html`, …). Increment from the highest existing version in that subfolder. Never overwrite or rename a previous iteration.

**New feature areas** get a new kebab-case subfolder under `design/`. **Non-HTML assets** use descriptive kebab-case names.

**Sage palette** in `design/mockups/v1.html` is the locked source of truth; `mobile/src/ui/theme.ts` carries it into the app.

## What NOT to do

- **No `number` for money.** Decimal strings and `bigint` only.
- **No `Intl` in the domain**, and check any new JS API against Hermes before relying on it.
- **No mocking Supabase in domain tests.** The domain is pure and needs no mocks. Integration checks run against the local stack.
- Do not break persisted data, deployed contracts, authentication identities, or older installed clients. Production changes require an explicit compatibility and rollout plan.
- Do not edit `mobile/ios` or `mobile/android` by hand; they are regenerated.
- **No emojis in code or commits** unless the user explicitly asked for them.

## Running things

```bash
# Local backend (Docker) and app config
bash supabase/scripts/start_local.sh
bash supabase/scripts/configure_mobile_local.sh

# App
cd mobile
npm install
npx expo run:ios                     # simulator
npx expo run:android                 # emulator; run supabase/scripts/connect_android_emulator.sh first

# Checks
npm run typecheck
npm test
npx prettier --check "src/**/*.{ts,tsx}"

# Static SQL source assembly check only; does not connect to a database
bash supabase/tests/00_sql_assembly.sh
```

### Development sign-in

Development builds pointed at the local stack show one-tap sign-in for the seeded fictional users (`mock@tab.local`, `alex@tab.local`, `sam@tab.local`, password `local-only-password`). Email codes from the local stack arrive in Mailpit at http://127.0.0.1:54324. The simulator can't do Sign in with Apple; use these instead.

## Task completion

Continue an authorized change through implementation, affected checks, and fixes for failures it causes. Choose routine reversible details from the established architecture. Ask only for missing facts or decisions that materially change the result. The production and migration boundaries above remain in force.

Select validation by changed behaviour: vitest for domain and data logic, `npm run typecheck` for app code, the simulator or emulator for UI flows, and isolated database checks for SQL changes. Documentation-only edits need content, links, and diff checks. Do not rerun passing suites without a change or unresolved concern.
