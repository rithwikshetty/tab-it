# Expenses Scroll Stall

## Goal

- Diagnose and fix the delay before the Expenses tab starts scrolling after opening or returning to an active trip.

## Log

### 2026-06-14

- Started investigation from the reported symptom: the Expenses tab in an active trip initially ignores or delays scrolling for roughly 2-3 seconds, while other tabs behave normally. The first hypothesis set will focus on Expenses-only render work, list identity churn, image loading, and broad sync/query invalidation.
- Read `TripDetailView`, `ExpenseRow`, and the presenter layer. The expenses list is a `ScrollView` containing nested eager `VStack`s, so every day, block, swipe row, and expense row can be built before the first scroll. `ExpenseRow` does not render receipt images, so receipt thumbnails are not the direct list-scroll cause.
- Applied the targeted UI fix in `TripDetailView`: the timeline and grouped expense cards now use `LazyVStack`, and expense block identity no longer concatenates every row UUID. This should reduce main-actor render work on first opening and on returning to the Expenses segment.
- Adjusted `SwipeToDeleteRow` so its horizontal delete drag runs simultaneously with the parent `ScrollView` rather than as an exclusive row gesture. The existing horizontal-axis guard still owns delete swipes, while vertical pans can scroll immediately.
- Validation: XcodeBuildMCP app unit tests passed (`TabTests`, 67/67). A full simulator test attempt compiled and ran 73/74 tests but failed the unrelated screenshot-tour UI test because its seeded trip was not listed.
- User reported the stall still reproduces, especially during fast tab switching. Reopened diagnosis. Current strongest hypothesis: rapid segment changes stack explicit segmented-control animations plus `TripDetailView` opacity transitions around a conditional `ZStack`, so SwiftUI can keep stale tab bodies alive while rebuilding the expenses timeline.
- Simulator repro loop with demo data: launched with mock auth and `TAB_SEED_DEMO=1`, opened Lisbon Long Weekend, rapidly tapped Balances/Overview/Expenses, then sent a scroll-view swipe. The snapshot stayed unchanged after both fast and slow swipes, confirming a stuck-scroll state. Tightened root cause: the custom row-level drag recognizer is still in the scroll path, and rapid tab switching makes the bad state easier to hit.
- Applied the stronger simplification: segment taps no longer create explicit animation transactions, `TripDetailView` no longer wraps tab content in an animated opacity-transition `ZStack`, and Expenses/settlement rows are plain tappable buttons rather than custom swipe-to-delete drag rows. Delete remains available from the detail screens.
- Added a regression seam: a debug-only `TAB_RESET_LOCAL_STORE=1` launch env resets SwiftData before demo seeding, and `TripDetailScrollUITests.testExpensesScrollAfterRapidSegmentSwitching` launches a clean seeded trip, rapidly switches segments, swipes the Expenses scroll view, and expects the lower `Airbnb in Alfama` row to appear.
- Validation after stronger fix: simulator replay with XcodeBuildMCP now scrolls after the same rapid segment switching that previously froze the scroll view. `TabTests` passed 67/67, the new `TripDetailScrollUITests` regression passed, and the screenshot-tour test passed after making its Airbnb scroll step explicit.

### 2026-06-19

- Reopened: user reports the Expenses tab still freezes for a couple of seconds and scrolls roughly right after opening the app and tapping a trip; other tabs feel fine. They asked for a long-term, fully scalable fix (and granted Supabase DB access), not another targeted patch.
- Re-read the render + data path end to end. Confirmed receipt images are NOT the list cost: `ExpenseEntity` stores only `receiptStoragePath: String?`; images live in Supabase storage and are fetched on demand in detail screens, not in `ExpenseRow`.
- Confirmed the per-render derivation cost: `TripDetailView.content(for:)` computes `BalancePresenter.summaries` on EVERY body pass (all tabs) and `TimelinePresenter.days` on every Expenses-tab pass, INLINE in `body`. Both filter `trip.expenses`, map each via `toCoreExpense()` (faulting `payments` + `splits` SwiftData relationships), run `BalanceEngine.compute`, then sort/group/format. No memoization: any unrelated re-render recomputes the whole timeline synchronously on the main actor. `MoneyFormatter` already caches `NumberFormatter`s, so it is not a suspect.
- Identified the dominant scalability villain: `SyncService` is `@MainActor` and `pullAll()` does full-table `select()`s with no per-trip filter (`expenses`, `expense_payments`, `expense_splits`, etc. — ALL rows across ALL trips), decoding + merging + saving them on the main thread. `RootView.task` runs `pullAll()` on every cold launch, and `RealtimeService.handleChange` runs it again on every live change. `performPullAll` issues ~10 separate `mainContext.save()` calls, each invalidating the on-screen `@Query` and forcing a fresh full re-render of `TripDetailView`. As total data grows, this main-thread sync work freezes the UI exactly when the user opens a trip; the Expenses tab (heaviest default screen) shows it worst.
- Secondary scroll-jank contributor: the 6 category icons are SVGs with `preserves-vector-representation: true`, which keeps the vector and re-rasterizes at display size rather than caching a bitmap — a per-row cost as `ExpenseRow`s realize during scroll. The nested `LazyVStack`-inside-`LazyVStack` in `timelineSection` is also unnecessary.
- View-state value types (`TimelineDay`, `ExpenseRowItem`, `BalanceSummary`, `OverviewState`, …) are already `Hashable, Sendable`, so snapshotting/memoizing derived state and rendering from immutable values is clean and SwiftUI-diff-friendly.
- App target is `Apps/Tab/Tab.xcodeproj` with individual (non-synchronized) file references, so new files need pbxproj registration; prefer keeping changes in existing files where practical.
- Launched a parallel diagnostic workflow (4 hypothesis agents + synthesis) to confirm/refute and rank causes before committing to the fix.
- Workflow verdict (converged): one dominant bug — the derived Expenses view-state (`summaries`, `timelineDays`, and the toolbar `ShareLink`'s `exportItem`) is computed inline in `body`, so the launch sync pull's ~10 `mainContext.save()`s and every scroll-driven invalidation each re-run the faulting, O(expenses x splits) presenters on the main actor. Amplifiers: cold SwiftData relationship faulting, the eager export-workbook build, the nested `LazyVStack`, and `minimumScaleFactor`. The robust fix is to memoise the derived state into the already-`Sendable` value types and recompute only on a content-signature change.
- Correction to one workflow claim: `SyncMerge.apply(TripDTO)` only assigns `lastActivityAt` when `dto.lastActivityAt > entity.lastActivityAt` (SyncMerge.swift:88-90), so a genuinely warm relaunch with no server change leaves the row clean and SwiftData fires no `@Query` refresh for the empty save. The storm therefore fully materialises only on the first/cold pull or when data actually changed — which is exactly what memoisation neutralises. No `lastActivityAt` change is warranted; it is correct server-trigger metadata and is deliberately kept out of the new signature.

### 2026-06-19 — implemented fix (Tier 1) + validation

- Implemented the memoisation fix, scoped to existing files (the app target uses individual pbxproj file refs, so no new files):
  - `ViewState.swift`: added `OverviewState.empty` as the pre-load placeholder.
  - `TripDetailView.swift`: the balance summaries, expense timeline, overview, and export workbook are now `@State` snapshots (`summaries`, `timeline`, `overview`, `exportData`) rebuilt once in `recomputeDerived(for:)`, driven by `.task(id: contentSignature(for:))`. `contentSignature` is a cheap value-typed fingerprint over top-level columns (counts, deleted counts, and max `updatedAt` across expenses+payments+splits+settlements+people+categories, plus `trip.updatedAt`, current person id, and current user name) — it reads only already-held rows, never runs a presenter, and stays identical across sync saves that change nothing, so those saves trigger no recompute. The body and toolbar render from the snapshots; the `ShareLink` reads cached `exportData` (falling back to a live build only before the first snapshot lands).
  - Flattened the per-card inner `LazyVStack` to a plain `VStack` (a block is one bounded card already realised by the outer `LazyVStack`; the inner laziness only cost layout).
  - Guarded the "No expenses yet" / "Everyone's settled" / empty-balance states behind `derivedLoaded` so the one-frame pre-compute pass never flashes an empty state.
  - Net effect: per-render main-thread work drops from O(renders x expenses) to O(content-changes x expenses). Scrolling and sync churn now read immutable snapshots and run no presenter.
- Validation (all green): `build_sim` clean (0 warnings, 0 errors, Swift 6 strict concurrency); `cd Packages/TabCore && swift test` 127/127; app unit `TabTests` 67/67; `TabUITests` 8/8 — including `TripDetailScrollUITests` (the scroll regression), `ScreenshotTourUITests` (navigates into a trip and scrolls to "Airbnb in Alfama"), and `PaidByFlowUITests` edit-expense flows (which confirm the content signature detects edits and recomputes). One earlier UI-test run hit a transient "Simulator … Busy (preflight)" launch flake; passed cleanly on retry after booting the sim.
- Supabase check (read-only, project `tab-it` / `gaseuxsieddlksxtdliq`, PG 17.6): the freeze is not DB-side. Performance advisors are INFO-only (one unindexed FK `expenses_last_edited_by_fkey`; unused indexes on `expenses.category_id`, `settlements_trip_active`, `activity_log_entity`). Security `SECURITY DEFINER` warnings are the intentional RPC write-path architecture documented in CLAUDE.md; `pg_net`-in-public and leaked-password-protection are pre-existing and out of scope. There is no `updated_at` index, which a future delta-sync would require.

### 2026-06-19 — deferred scalability roadmap (not implemented; needs real-data testing + user sign-off)

Deliberately NOT done overnight because they touch the sync core and cannot be integration-tested without a real Supabase session and seeded remote data. Tier 1 already removes the user-visible freeze/jank and scales rendering; these would harden the data layer further:

1. Coalesce `performPullAll`'s ~10 `mainContext.save()`s into one (stage all `apply()`s, save once, then reconcile). Reduces app-wide `@Query` thrash (trip list / friends / activity also re-render ~10x per pull). Risk: depends on `ModelContext.fetch` reflecting unsaved pending inserts so child rows (payments/splits) still link to just-inserted parent expenses — verify that SwiftData semantics with a focused in-memory test before changing, and keep per-table fetch-failure isolation.
2. Move sync decode + merge off the main actor (a SwiftData `ModelActor` background context). `SyncService` is `@MainActor` and `pullAll` decodes/merges full-table results on the main thread; this is the real "retrieving heavy information" cost as total data grows. Biggest scalability lever, broadest concurrency change.
3. Incremental/delta pulls: filter pulls by `updated_at > cursor` (persist a per-table cursor), leaning on soft-delete tombstones for deletions and a periodic full reconcile to catch 30-day hard purges. Requires adding `(updated_at)` / `(trip_id, updated_at)` indexes (none exist today) and careful delete-detection design.
4. Optional rendering polish, gated on profiling a large trip: move the heavy derivation (BalanceEngine + grouping + formatting) off the main actor by first snapshotting entities to `Sendable` TabCore values on main, then computing on a detached task — would require refactoring the presenters to accept `Sendable` inputs (shared with the trip list / friends, so higher blast radius). Re-evaluate `minimumScaleFactor` on `ExpenseRow` only with a real profile.
