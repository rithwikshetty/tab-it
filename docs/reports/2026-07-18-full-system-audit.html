How the fixes were done

The 20 findings were grouped into five workstreams so related fixes travelled together and unrelated ones couldn't collide. Each workstream ran in its own isolated copy of the repository (a git worktree) with Codex (GPT-5.6 Sol) writing all the code, test-first. Claude acted as architect only: wrote the specifications, reviewed every diff line-by-line, ran the test suites independently, and merged the branches into main one at a time.

Every finding was tracked as a GitHub issue (#13–#32, label audit-2026-07-18) with comments recording when work started, what changed, and the commit that fixed it. 17 issues are closed; #18, #19, and #28 stay open until the gated deployment steps below run.

Verification on the final merged code: 155 TabCore logic tests, 116 app tests (21 of the 271 are new, covering each fix), and the SQL assembly check — all green. The live production database was never touched at any point; every database change exists only as repository files until you approve applying them.

Five words to know

Sync
The app stores everything on the phone first, then exchanges changes with the server. Push means sending your changes up; pull means downloading everyone else's changes.
Reconcile
After a pull, the app compares what the server sent with what the phone has, and deletes local copies of anything the server no longer has. Safe only when the server's answer is complete — the root of bug #1.
Last-write-wins (LWW)
When two people edit the same thing, the edit with the later timestamp is kept. Deletions are meant to beat edits ("delete-wins").
writeID
A unique stamp on every save. The app compares stamps to know whether a row still has unsent changes.
Tombstone
A deleted record is not erased immediately — it is marked deleted and kept for 30 days. That marker is called a tombstone.

High severity — could silently lose or corrupt data

FixedWas: High1. Big trips corrupted themselves past the server's 1,000-row response cap

The bug: pulls asked for everything in one request; the server silently stops at 1,000 rows; the app then deleted any local record missing from the truncated answer. A 6-person trip with ~170 shared expenses crossed the line.

The fix: every pull now fetches in stable-ordered pages until the set is provably complete, and the delete-reconcile step only ever runs against a complete set. If any page fails, reconciliation is skipped for that table — exactly the pre-existing failure behavior. The activity feed keeps its intentional newest-300 cap, since its results are display-only and never reconciled.

Commit cb77c90 (+ 9c2ff6d) · new PaginatedFetch.swift with 4 unit tests · issue #13 closed

FixedWas: High2. Edits made while a save was in flight were marked "sent" but never sent

The bug: after a request finished, the app acknowledged the record's current write stamp — which, if you edited or deleted mid-request, belonged to a newer change the server never received. That change silently stayed on your phone only.

The fix: every push path now snapshots the write stamp before sending and acknowledges only that captured value. A change landing mid-request keeps the record marked "dirty", so it is pushed on the next cycle. Applied across all 22 acknowledgment points (profile, trips, people, settlements, expenses with their payments and splits).

Medium severity

FixedWas: Medium3. A pull and a push at the same time could make an expense vanish briefly

The fix: pushes and pulls now run through a strict first-in-first-out gate — they can never interleave, and queued work is never dropped. The gate's ordering guarantees have their own unit tests.

Commit cb23746 · new ServiceConcurrency.swift · issue #15 closed

FixedWas: Medium4. Switching trips quickly leaked a live server connection

The fix: each subscription attempt carries a generation number and re-checks it after every wait point; a superseded attempt tears down everything it created. Any sequence of rapid switches now ends with exactly one live connection, for the trip you're actually viewing.

Commit d0b68d6 · issue #16 closed

FixedWas: Medium5. Changing currency mid-entry could save impossible amounts

The fix: switching currency now converts the exact per-payer amounts through the same value-preserving normalization as the splits, and saving requires every individual payment — not just the total — to be valid for the chosen currency.

Commit 1f1c565 · new pure ExpensePaymentLedger helper, unit tested · issue #17 closed

Fixed in repoWas: Medium6. The database only half-enforced "deletion beats edit"

The fix: the database trigger now applies an incoming deletion unconditionally when the row is live (matching the app's rule exactly); reviving a deleted record stays blocked. Covered by new database tests.

Commit b5ab7dd · issue #18 open — needs the production schema apply (gated)

Fixed in repoWas: Medium7. One wrong push-notification setting would permanently unregister every device

The fix: only genuinely dead tokens (Apple's 410 / "Unregistered") are deleted now. "BadDeviceToken" — which also means a server environment mismatch — is kept and logged with a warning naming the misconfigured setting. The classification is a pure function with its own tests.

Commit 5d5017d · issue #19 open — needs the edge function redeploy (gated)

FixedWas: Medium8. A stale database test was failing and masking regressions

The fix: suite 08 now asserts the current function signature and the current unread-count semantics, with deterministic timestamps proving the expected counts rather than fudging numbers.

Commit fc0e77e · issue #20 closed

FixedWas: Medium9. Sign-out pretended to succeed even when it didn't

The fix: a failed server sign-out is now logged and followed by an explicit local-session wipe, so the old session can't resurface on the next launch. Signing out while offline still works.

Things that looked like bugs but aren't

Unchanged from the audit: four claims were disproven during verification (including "production push is broken by a development entitlement" — it isn't), and two conflict-resolution behaviors are documented as deliberate (two-tombstone ordering by deletion time; clean local rows always accepting the server's version). No floating-point money exists anywhere — both independent audits checked.
